## 1. Critical Ref-Mutation Bugs (Zustand Anti-Patterns)

Zustand relies on strict object-reference changes (`===`) to determine if a component needs to re-render. In a few of your folder and variable methods, you are performing a shallow copy of the top-level `graphs` container, but **directly mutating its nested object references**. This bypasses state change detection.

### The Issue in `renameFolder` & `deleteFolder`

```javascript
// Current Implementation
const newGraphs = { ...state.graphs };
Object.keys(newGraphs).forEach((gKey) => {
  if (newGraphs[gKey].folder === oldName) {
    newGraphs[gKey].folder = newName; // ❌ MUTATION! Modifies the original object reference.
  }
});

```

Because `newGraphs[gKey]` points to the exact same reference in memory as `state.graphs[gKey]`, any React components or selectors listening to that specific graph won't realize its folder property changed.

### The Issue in `updateVariable`

```javascript
// Current Implementation
Object.keys(updatedGraphs).forEach((gKey) => {
  updatedGraphs[gKey].nodes = updatedGraphs[gKey].nodes.map((node) => { ... }) // ❌ MUTATION!

```

You are writing directly to the `nodes` property of the uncopied graph reference.

### 🛠️ The Fix

Rebuild those branches cleanly by copying the targeted graph object during iterating loops:

```javascript
// In renameFolder:
Object.keys(newGraphs).forEach((gKey) => {
  if (newGraphs[gKey].folder === oldName) {
    newGraphs[gKey] = {
      ...newGraphs[gKey],
      folder: newName
    };
  }
});

// In updateVariable:

  updatedGraphs[gKey] = {
    ...updatedGraphs[gKey],
    nodes: updatedGraphs[gKey].nodes.map((node) => { ... })
  };
});

```

## 2. Storage Scalability (The 5MB LocalStorage Ceiling)

You are using `createJSONStorage(() => localStorage)`. LocalStorage has a strict, hard boundary limit of **~5MB** depending on the browser.

As your projects expand into dense narrative trees—containing hundreds of localized graphs, unique scene schemas, complex node data arrays, routing registries, and dialogue content—**you will quickly throw a `QuotaExceededError`.**

### 🛠️ Recommendation: Migrate to IndexedDB

IndexedDB gives your application access to hundreds of megabytes (or gigabytes) of persistent storage natively. You can swap this out without altering any business logic by integrating a tiny library like `localforage` or `idb-keyval` into your store storage adapter configuration.

```javascript
import { get, set, del } from "idb-keyval";

const indexedDBStorage = {
  getItem: async (name) => (await get(name)) || null,
  setItem: async (name, value) => { await set(name, value); },
  removeItem: async (name) => { await del(name); },
};

// Then update your persist options block:
{
  name: "lore-engine-storage",
  storage: createJSONStorage(() => indexedDBStorage),
}

```
